## 0. 先建立心智模型

一个大模型（如 Llama、Qwen）出厂时已在海量互联网数据上做过 **预训练（pre-training）**，是个"通才"——什么都懂一点，但不一定懂你的业务、不一定按你要的格式说话。**微调（fine-tuning）** 就是拿这个通才，用你自己的一批数据再训练一小段，让它变成更适合你任务的"专才"。

打个比方：预训练模型像名校毕业的应届生，通识强；微调就是岗前培训，让他熟悉你们的业务流程和话术。

### 为什么要微调？几个 use case

前提：微调 **不是** 唯一手段。很多时候 **提示工程（prompt engineering，写好提示词）** 或 **RAG（检索增强生成，Retrieval-Augmented Generation，先检索知识库再让模型回答）** 就够了。微调通常在以下场景才值得做：

- **稳定输出特定格式/风格**：要模型永远输出严格 JSON、永远用某种公司话术。Prompt 能做到但不稳定，微调能"刻进肌肉记忆"。（很接近 EWP 风险分类场景。）
- **注入领域知识/专业能力**：通用模型不懂你们内部术语、产品、合规规则，微调让它懂。
- **让小模型达到接近大模型的效果（省钱）**：用 GPT-4/Claude 太贵太慢，可用大模型生成一批高质量答案，拿这批数据微调一个 7B 小模型，让它在特定任务上接近大模型但成本低 10–100 倍。这叫 **知识蒸馏（knowledge distillation）**。
- **对齐人类偏好/安全性**：让回答更符合人类喜好、更安全、会礼貌拒绝。用 DPO/RLHF 这类偏好对齐方法。

**一句话判断**：缺知识 → 优先 RAG；不会按要求干活 / 要小模型省钱 → 微调。两者也常一起用。

### 整体流程

```
数据准备 → 选基座模型 → 选微调方法 → 训练（调参） → 评估 → 注册/部署 → 监控
                ↑                                                        │
                └───线上 bad case 回收 → 进数据集（数据飞轮 data flywheel） ←─┘
```

下面逐阶段展开。

## 1. 数据准备（最耗时，占 60%+ 工作量）

### 数据格式

通常是 **JSONL**（JSON Lines，每行一个独立 JSON 对象的文件格式），每行一条样本，核心是"输入→期望输出"的配对：

```jsonl
{"messages": [{"role": "system", "content": "..."}, {"role": "user", "content": "..."}, {"role": "assistant", "content": "..."}]}
```

模型看这些例子学会"遇到这种输入该这样回答"。

### 数据从哪儿来、怎么收集

- **公司内部已有数据**（最常见、最有价值）：历史客服对话、工单、问答日志、内部文档（可用大模型转成问答对）、业务数据库。
- **人工标注**（质量最高、成本最高）：雇标注员或内部专家针对一批输入写标准答案。流程：准备输入 → 写标注指南 → 标注 → 质检 → 多人标注算一致性（看下面的[标注一致性怎么衡量](#标注一致性怎么衡量cohens-kappa)）。金融/医疗常这么做。
- **合成数据（synthetic data，现在极流行）**：用 GPT-4/Claude 批量生成样本，快、便宜、量大，但要过滤错误，还要注意目标模型的服务条款是否允许用其输出训练。
- **公开数据集**：HuggingFace Hub、Kaggle 上的开源指令数据集（Alpaca、OpenOrca、UltraChat），通常用来补充通用能力。
- **用户反馈回流（数据飞轮，data flywheel）**：上线后把点赞/点踩、人工纠正的 bad case 收集进下一轮训练，形成循环。

**典型量级**：SFT 阶段几千到几十万条高质量样本通常够用。**质量远比数量重要**——1000 条精标往往胜过 10 万条噪声。

#### 标注一致性怎么衡量：Cohen's Kappa

**Cohen's Kappa** 衡量 **两个标注员之间的一致性（inter-annotator agreement）**——他们独立标同一批数据有多一致，且 **扣掉了"瞎猜也会蒙对"的部分**。比如二分类乱标也有 50% 概率碰巧一致，Kappa 把这种随机一致性减掉。取值 −1 到 1，>0.8 很好，0.6–0.8 不错。

注意它 **不是** ground truth adherence：**Cohen's Kappa** 不需要标准答案，只问"两个人是否互相同意"。

标注阶段用 Kappa 而非 adherence，是因为这时 **还没有标准答案**——标准答案恰恰是你想通过标注建立的。一致性高才说明任务定义清晰、质量可靠；一致性低说明标注指南有歧义，得回去改。

### 清洗去重：MinHash / SimHash

**为什么去重**：训练数据若有大量高度相似样本，模型会过拟合（背下来）、浪费算力。但精确去重（一字不差才算重复）抓不住"改了几个字"的近似重复；而逐两两比较所有文档是平方级计算量（100 万文档要比 5000 亿次），不可行。

**MinHash / SimHash** 都是 **近似去重（near-duplicate detection）** 算法，共同思想是：把每个文档压成一个短"指纹"，相似文档指纹也相似，比指纹远快于比全文。

- **SimHash**：把文档变成固定长度（如 64 位）的二进制指纹。关键性质——内容越相似，两指纹的 **汉明距离（Hamming distance，有多少位不同）** 越小。只差几位 → 判为重复。Google 早年用它给网页去重。
- **MinHash**：用来估计两集合的 **Jaccard 相似度（交集大小 / 并集大小）**，文档常表示成 "shingle"（连续 n 个词的片段）的集合。对所有 shingle 用多个哈希函数各取最小值得到签名，两签名相同比例 ≈ Jaccard 相似度。通常配 **LSH（Locality-Sensitive Hashing，局部敏感哈希）** 分桶：相似文档大概率落进同一桶，只在桶内比较，避免全量两两比对。
- **一句话区别**：SimHash 估"按位的相似"，MinHash 估"集合（词片段）的重叠度"。大规模文本去重 MinHash+LSH 用得更多。

### 数据配比（data mixing）：领域数据 vs 通用数据

先解释 **SFT = Supervised Fine-Tuning（监督微调）**，"监督"指每条样本都有明确的标准答案（label），模型学着模仿。SFT(以及其他方式)阶段通常掺两类数据：

- **领域数据（domain-specific data / in-domain data）**：与你目标任务直接相关的数据。做金融新闻风险分类，金融新闻 + 风险标签就是领域数据。
- **通用数据（general data / general-purpose data）**：与任务无关、覆盖各种日常能力的数据（对话、常识、写作、推理），来源通常是公开指令数据集。

**指令数据集（instruction dataset）** 就是通用数据的典型形态——一堆"指令 + 期望回答"的配对，教模型 **follow 各种人类指令**：

```jsonl
{"instruction": "把下面这句话翻译成英文", "input": "今天天气很好", "output": "The weather is nice today."}
{"instruction": "用三句话总结这段文字", "input": "...", "output": "..."}
{"instruction": "写一首关于秋天的诗", "input": "", "output": "..."}
```

它覆盖各种任务类型（翻译、总结、问答、写作、推理……），目的是让模型从"只会续写文本"变成"你让它干啥它干啥"。它和领域数据的区别只在内容范围：指令数据集是"什么任务都有"的通才训练料，领域数据是"专攻一个任务"的专才训练料，格式上两者一样。

**为什么掺通用数据**：只用领域数据猛训会"只会这一件事，别的全忘"——即下面的灾难性遗忘。通常掺 5%–30% 通用数据，能在学新任务的同时保住通用能力。

#### 灾难性遗忘（catastrophic forgetting）

模型学新任务时 **严重丢失之前已掌握的能力**。直观理解——模型的知识存在权重（参数）里，微调会改动权重；若只拿很窄的数据猛训、训太多轮，编码通用能力的那部分权重被覆盖掉，结果是新任务变强了但突然不会做数学、中文变差、常识答错。

- **典型表现**：你的任务指标很漂亮，但跑通用 benchmark（如 MMLU）大幅掉点。
- **缓解**：①掺通用数据；②用 LoRA 等只改一小部分参数的方法（基座几乎不动，天然不易遗忘）；③学习率别太大、轮数别太多；④训练前后都跑 benchmark 对比监控。

### 格式校验：chat template 对齐

模型训练时见到的对话不是 `{"role":"user","content":"你好"}` 这种结构化数据，而是被拼成一长串带 **特殊标记（special tokens）** 的纯文本。**chat template（对话模板）** 就是"把多轮对话拼成这串文本"的格式规范。不同模型家族格式完全不同（示意）：

- Llama 3 系：`<|start_header_id|>user<|end_header_id|> 你好 <|eot_id|>...`
- Qwen 系：`<|im_start|>user\n你好<|im_end|>\n<|im_start|>assistant`

这些 `<|im_start|>`、`<|eot_id|>` 就是特殊标记，模型靠它们识别"这是用户说的""该我 assistant 开始答了"。

**"对齐基座模型" = 你微调用的 chat template 必须和基座模型预训练时用的完全一致。** 若用错（拿 Qwen 却套 Llama 模板），模型识别不出角色边界，相当于用它没见过的暗号说话，训练效果大幅下降、推理时还可能不知何时停。**实操**：用对应模型的 tokenizer 调 `apply_chat_template()` 会自动按官方模板拼接；坑常出在手动拼字符串、训练和推理用了不同模板。

### 数据集划分：train / validation / test

切三份是为了 **诚实评估模型学得好不好、有没有过拟合作弊**。

| | 用在何时 | 用来干什么 | 是否影响模型选择 | 占比 |
|---|---|---|---|---|
| **训练集 training set** | — | 模型真正"学习"用，反复看并调权重 | — | ~80% |
| **验证集 validation set / dev set** | 训练 **过程中** 反复用 | 调参、选模型、监控过拟合、决定 **早停（early stopping）** | **会** | ~10% |
| **测试集 test set** | 训练 **结束后** 用一次 | 报告最终真实性能 | **不会** | ~10% |

**为什么分开 validation 和 test**：你一旦根据某份数据反复调参，它就"间接泄露"进决策，成绩偏乐观。验证集已被"用脏"，所以需要一份从头没碰过的测试集给出诚实分数。

> 比喻：训练集 = 平时练习题；验证集 = 月考（据此调复习策略）；测试集 = 高考（一次性、决定性、之前绝不能见过题）。

### 用到的工具：Spark 在数据准备阶段

**Apache Spark** 是 **分布式数据处理框架**——把一个超大数据处理任务拆开分到很多台机器并行跑。它用在 **数据准备阶段，不在训练阶段**（训练用 GPU + PyTorch；Spark 是训练前把脏数据加工成干净样本）。只有数据量大到单机内存装不下时才需要它，几万条用 pandas 单机就够。

Spark 在这一步具体干：①从数据湖（S3/HDFS 上 TB 级日志）大规模读取；②清洗过滤（去空、去过短过长、去含 PII 个人身份信息的样本，把几亿行分到上百节点并行）；③去重（MinHash 近似去重在 Spark 上有成熟实现）；④格式转换成 JSONL；⑤按比例采样混合（data mixing）；⑥统计 token 长度/类别分布。

```python
from pyspark.sql import SparkSession
spark = SparkSession.builder.appName("data-prep").getOrCreate()
df = spark.read.json("s3://my-bucket/raw-conversations/")     # 读海量原始数据
df = df.filter(df["content"].isNotNull())                     # 分布式过滤
df = df.dropDuplicates(["content"])                           # 分布式去重
df.write.json("s3://my-bucket/cleaned-sft-data/")             # 写回训练格式
```

你写逻辑，并行调度由 Spark 负责。**和 Amex 场景的关系**：你在 GCP Lumi 跑 Airflow DAG，那种"大规模、定时、多阶段处理数据"的流水线里，数据预处理常用 Spark（GCP 上对应 Dataproc 跑 Spark，或 BigQuery）。**Airflow 负责编排调度（何时跑哪步），Spark 负责具体把那一大步的数据算完。** 其它常用库还有 Ray，以及 HuggingFace `datasets` 做加载处理。

## 2. 选基座模型

**基座模型（base model / foundation model）** 就是你拿来微调的"出厂预训练模型"。选它权衡这几个维度：

- **模型规模（参数量）**：1B/3B/7B/8B/14B/32B/70B（B = billion，十亿参数）。越大越聪明但越贵越慢越吃显存。经验：先用 7B/8B 试水（性价比甜区），不够再往上。
- **Base 版 vs Instruct 版**（见下）。
- **开源 vs 闭源**：开源（Llama、Qwen、Mistral、Gemma）权重能下载、可自部署、数据不出公司——金融/医疗合规敏感行业基本只能选这条；闭源（GPT、Claude、Gemini）只能通过微调 API、拿不到权重（见下）。
- **License（许可协议）**：必须确认协议 **允许商用**，企业法务这关绕不过。
- **能力匹配/排行榜**：看 Open LLM Leaderboard、Chatbot Arena 和任务相关 benchmark；看是否支持长上下文、多语言（做中英文场景，Qwen 系中文强）、function calling。
- **生态与社区**：框架支持（vLLM、transformers）、案例和文档是否完善。

**实操建议**：中英文金融场景，**Qwen 系**（中文强、协议友好）或 **Llama 系**（生态最全）的 7B/14B Instruct 版是稳的起点。

### Base 版 vs Instruct 版，各用来干嘛

- **Base 版**：只做了预训练，不会聊天、不会 follow 指令，是"半成品"。主要给两类人用：①要做大幅度行为改造的团队（Instruct 版已被官方调教出固定风格/安全策略，若你想要的行为和它冲突，不如从干净的 Base 版从头 SFT）；②做研究/自建完整后训练流程的团队（要研究 SFT→DPO→RLHF 每一步，得从 Base 起步，因为 Instruct 已是别人走完流程的成品）。
- **Instruct/Chat 版**：已做过指令微调、会聊天会 follow 指令。**99% 的业务微调都该用它**——你只是想在一个会说话的模型上加领域能力，没必要重新教它怎么说话。

### 闭源微调 API 怎么用、效果如何、金融能不能用

**怎么用**：闭源厂商提供托管微调，你不碰权重，只走 API：

```python
# OpenAI 为例（概念示意）
client.files.create(file=open("train.jsonl","rb"), purpose="fine-tune")          # 1. 上传 JSONL
client.fine_tuning.jobs.create(training_file="file-xxx", model="gpt-4o-mini-...") # 2. 启动任务
# 3. 训完拿到专属模型 ID
client.chat.completions.create(model="ft:gpt-4o-mini:org::xxxx", messages=[...])  # 4. 调用你的微调版
```

能调的超参很有限（通常就 epochs、learning rate multiplier、batch size），底层是黑盒。

**效果**：对格式对齐、风格统一、特定任务模式这类需求效果好且省心，不用管 GPU。但你完全受制于厂商：旋钮少、看不到内部、模型可能被下线或涨价、没法自己做 DPO/RLHF。

**金融能不能用**：**通常受严格限制，很多场景不能用**。原因：①**数据出域**——API 要求把训练数据上传到厂商服务器，金融数据受合规约束（GLBA、各州法规、内部数据治理）通常不允许离开可控环境，这条往往直接否决；②数据驻留与审计要求第三方黑盒满足不了；③模型可控性——托管模型被厂商单方面更新/下线的风险不可接受。所以金融/医疗 **绝大多数走开源模型 + 公司可控环境自己微调** 的路线（也是 Amex 用 GCP 内部环境的原因）。例外：厂商提供企业版/VPC 内微调（数据不出租户、有 BAA/DPA 协议）且过了法务安全评估，某些场景可逐案审批使用。

## 3. 选微调方法

这里有两个正交的维度：**改多少参数**（方法）× **用什么目标训**（范式），可自由组合，如"用 LoRA 做 SFT"。

### 维度一：改多少参数

| 方法 | 显存占用 | 效果 | 场景 |
|------|---------|------|------|
| **Full Fine-tuning 全参微调** | 极高 | 最好 | 数据多、预算足、要改模型核心能力 |
| **LoRA** | 低 | 接近全参 | 主流选择，性价比最高 |
| **QLoRA** | 极低 | 略低于 LoRA | 单卡/资源受限 |
| **Prefix/Prompt Tuning** | 最低 | 一般 | 轻量任务 |

- **Full Fine-tuning（全参微调）**：更新所有参数，效果最好但显存和成本极高。
- **LoRA（Low-Rank Adaptation，低秩适配）**：**冻结基座所有原参数不动**，只在旁边插入一组很小的可训练矩阵学"增量"。只训练极少参数（常 <1% 总量），显存存储大降，效果却接近全参。大公司主流。
- **QLoRA（Quantized LoRA）**：在 LoRA 基础上把基座 **量化（quantization，用更低位宽如 4-bit 存权重以省显存）** 后再训练，单张消费级卡也能微调大模型。
- **Prefix/Prompt Tuning**：只训练一小段"软提示"向量，最轻但能力一般。

#### LoRA adapter 是什么

LoRA 训练出来的那个 **小补丁文件**。因为只学了那点增量参数，所以：
- **小**：几十 MB（基座本体几十 GB）。
- **可插拔**：推理时基座 + adapter 一加载 = 微调后行为；不加载 = 原始基座。
- **可共享基座**：一个基座挂多个 adapter（任务 A 一个、任务 B 一个），按需切换。这就是 vLLM **multi-LoRA**——一份大基座常驻显存，多个几十 MB 的 adapter 动态加载，省显存省存储，也是大公司爱用 LoRA 的关键原因。

> 比喻：基座是标准款相机，adapter 是可换镜头。不改相机本体，换镜头就能拍不同题材。

### 维度二：用什么目标训（训练范式）

- **SFT（Supervised Fine-Tuning，监督微调）**：最常用。给"输入→标准输出"对，让模型学会按格式回答。
- **DPO（Direct Preference Optimization，直接偏好优化）**：偏好对齐，需要 **chosen/rejected 成对数据**。比 RLHF 简单，**不需要训练奖励模型**，是现在主流对齐方法。
- **RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习；常用 PPO 算法）**：最复杂。需先训一个 **奖励模型（reward model）**——专门给回答打分、学人类觉得哪种更好；再用强化学习让主模型（**policy model，策略模型**，被优化的那个）去最大化分数。训练不稳定、资源消耗大，被 DPO 逐渐替代。
- **GRPO（Group Relative Policy Optimization，组相对策略优化）**：见下。

#### DPO 的 chosen/rejected 是 good & less good，不是 good & bad

通常是 **两个都还行、只是一个更好**。DPO 本质是教模型"在两个都说得过去的回答里，人类更偏好哪种风格/语气/详略/安全程度"。理想的 rejected 不是"事实错误的烂答案"，而是"也对、但不如 chosen"——稍啰嗦、语气没那么礼貌、格式没那么规整。

为什么不用"明显错误"当 rejected：若 rejected 一眼假，模型只学到"别说假话"这种太容易的信号，区分度低。用势均力敌的两个答案，模型才被迫学"到底哪个更符合人类口味"的微妙边界。（实践中也会掺一些 chosen=安全/正确、rejected=有害/错误的对，强化安全和事实底线，但精髓在 good vs less good。）

#### GRPO 细说

**GRPO**，由 **DeepSeek 在 2024 年初** 提出（最早出现在 2024 年 2 月的 DeepSeekMath 论文），在 2025 年初的 **DeepSeek-R1** 上大放异彩，成为训练推理模型的明星方法。

它解决的痛点：传统 RLHF 用 PPO，需要额外训练并同时在显存里跑一个 **价值网络（value network / critic，估计"当前状态未来能拿多少奖励"的模型）**，又费显存又难训。

GRPO 核心思想——**用"一组答案互相比较"替代价值网络**：

1. 对同一个问题，让模型一次 **采样生成一组答案**（如 8 个或 16 个）。
2. 给这组答案各自打分（数学题就看答案对不对，可用规则自动判，不一定要奖励模型）。
3. **关键**：不用价值网络估基准，而是直接拿 **这组答案的平均分当基准**。每个答案的好坏 = 它的分 − 组平均分（这就是"组相对" relative 的来历）。比平均好的被强化，比平均差的被抑制。
4. 据此更新模型，让它更倾向生成"组内拔尖"的答案。

> 直观理解：与其训一个裁判告诉你"这道题大概该得 70 分"，不如让模型自己答 8 遍，用这 8 遍平均当基准——谁超过平均谁就是好的。省掉价值网络，显存和复杂度大降。

为什么适合推理任务：数学/代码有 **可自动验证的标准答案**，打分能用规则完成（对就 1、错就 0），不依赖奖励模型，配合组内比较就能高效把推理能力"刷"上去。DeepSeek-R1 的长思维链推理很大程度靠这套。

## 4. 训练与调参

### 关键概念：前向 / 反向

神经网络训练每一步包含两个阶段：

- **前向传播（forward pass，前向）**：把输入喂进模型，从第一层算到最后一层得到预测，再和标准答案比，算出 **误差（loss，损失）**——差多少。即"模型做了一次回答"。
- **反向传播（backward pass，反向）**：从误差出发，反着从最后一层往第一层倒推，算出"每个参数对误差贡献多少、该往哪调"——这个量叫 **梯度（gradient）**。优化器按梯度 + 学习率更新参数。即"模型从错误里学到该怎么改"。

一次完整训练步 = 前向（做题 + 算错多少）→ 反向（算出每个参数该怎么改）→ 更新参数。循环几千几万步，模型就学好了。**反向更吃显存（要用到前向的中间结果）**，所以有 `gradient_checkpointing` 这种省显存技巧。

### 超参数

**超参数（hyperparameter）** 是你训练前手动设定、控制训练过程的旋钮（区别于模型自己学出来的"参数/权重"）。

#### 通用训练超参

| 超参 | 含义 | 取值/说明 |
|---|---|---|
| `learning_rate` 学习率 | 每次参数更新的步长 | 全参 `1e-5~5e-5`；LoRA `1e-4~3e-4`。太大→震荡/发散；太小→收敛慢/学不动 (解释见下面) |
| `num_train_epochs` 轮数 | 整个数据集过几遍（1 epoch = 一遍） | SFT 通常 `1~3`，太多会过拟合 |
| `per_device_train_batch_size` 每卡批大小 | 每张 GPU 一次前向/反向处理多少样本 | 受显存限制，通常 `1~8` |
| `gradient_accumulation_steps` 梯度累积 | 累积 N 步梯度再更新一次，等效放大 batch | 有效 batch = batch_size × grad_accum × GPU 数 |
| `warmup_ratio` / `warmup_steps` 预热 | 初期学习率从 0 线性爬升，避免一上来打乱预训练权重 | `0.03~0.1`（前 3%–10% 步） |
| `lr_scheduler_type` 调度 | 学习率随训练如何变化 | 常用 `cosine`（余弦衰减）、`linear` |
| `weight_decay` 权重衰减 | L2 正则，惩罚大权重，防过拟合 | `0.0~0.1` |
| `max_seq_length` 最大序列长度 | 单条样本 token 上限，超出截断 | `2048/4096/8192`，越长越吃显存（注意力平方复杂度） |
| `bf16` / `fp16` 混合精度 | 用 16 位浮点训练，省显存提速 | `bf16`（A100/H100）数值更稳，首选 |
| `gradient_checkpointing` 梯度检查点 | 不存所有中间激活，反向时重算，时间换显存 | 大模型基本必开 |
| `max_grad_norm` 梯度裁剪 | 把梯度范数裁到上限，防梯度爆炸 | 常用 `1.0` |

**"太大→发散/震荡，太小→收敛慢/学不动"是什么意思**：用"下山找最低点"打比方，学习率是每步迈多大。
- **太大**：一步迈过头跨到对面山坡，反复横跳下不去（**震荡 oscillation**）；更极端越跳越高、误差飙升失控（**发散 diverge**，loss 抖动或变 NaN）。
- **太小**：方向对但每步挪一点点，走到谷底极久（**收敛慢**）；还可能卡在半山腰小凹陷出不来（**学不动**）。
- 所以要选"不大不小"的甜区。warmup + cosine 衰减就是一路动态调节步长。

#### LoRA 专属超参

| 超参 | 含义 | 取值/说明 |
|---|---|---|
| `r` rank 秩 | LoRA 小矩阵的秩，决定可训练参数量和表达力 | `8/16/32/64`，常用 16/32。越大越接近全参成本 |
| `lora_alpha` 缩放因子 | LoRA 输出缩放，实际比例 = alpha/r | 经验：alpha 设成 r 的 1~2 倍（如 r=16, alpha=32） |
| `lora_dropout` | LoRA 层 dropout（随机丢连接防过拟合） | `0.05~0.1` |
| `target_modules` 注入模块 | 往哪些层加 LoRA | `q_proj,k_proj,v_proj,o_proj`（注意力四投影）；要更好加 `gate_proj,up_proj,down_proj`（FFN）。注入越多越接近全参 |

#### DPO 专属超参

| 超参 | 含义 | 取值/说明 |
|---|---|---|
| `beta` | 控制对 **参考模型（reference model，微调前原模型副本）** 偏离的惩罚强度 | 常用范围 `0.01~0.5`，默认 `0.1` |

**beta 是大是小、最大是不是 1**：0.1 算偏小，且 **没有硬性上界**（理论上可 >1，不是 0–1 比例值）。
- beta 小（0.05/0.1）→ 惩罚轻 → 敢大幅改变、更激进学新偏好，但太小可能学偏。
- beta 大（0.5/1.0）→ 惩罚重 → 紧贴原模型、改动保守，对齐效果弱但更稳。
- 它是"惩罚强度系数"，一般从 0.1 起步。

### 训练用谁的 GPU：本地笔记本 vs 云端

**几乎无关，只看云端（SageMaker/GCP 等）分配的 GPU。** 微调 7B 以上模型显存动辄几十上百 GB，笔记本那块 GPU 扛不住。真正训练全跑在云端/集群的 A100/H100 上——你在笔记本写代码、提交任务，任务被调度到云端 GPU。本地 GPU 只用于跑小 demo、调试代码逻辑、本地推理量化小模型。典型工作流：本地写代码 → 推到云 → 申请 N 张 A100 跑训练 → 看 wandb 监控曲线。

### 怎么找到最好的超参组合

没人能一眼算出最优，都是"有章法地试"出来的：

1. **用社区验证过的默认值起步**，不要从零猜（如 lr=2e-4、r=16、alpha=32、epochs=3），先把 pipeline 跑通拿到 baseline。
2. **只调少数几个高影响旋钮**：LoRA 微调真正值得调的就 **learning_rate（影响最大）、epochs、r**，其余用默认。
3. **用搜索策略系统地试**：网格搜索（grid search，列候选组合全跑）/ 随机搜索（random search，范围内随机采样，组合多时更高效）/ 贝叶斯优化（Bayesian optimization，用 **Optuna / Ray Tune / W&B Sweeps** 根据已跑结果智能选下一组）。大公司基本用自动化工具。
4. **始终用验证集判优、盯过拟合**：选验证集最好的那组；训练集和验证集 loss 差距拉大就是过拟合，减 epochs 或加正则。
5. **成本意识**：每跑一组都烧 GPU。先用小规模数据 + 小模型筛掉明显差的，再用最优几组上全量精调。

一句话：**默认值起步 → 只调 lr/epochs/r → 用 Optuna 自动搜 → 始终用验证集选优 → 用小规模实验控成本。**

### Library 与 Platform

**Library（写训练代码用的库）**

- **HuggingFace `transformers` + `peft` + `trl`**：最通用组合。`transformers` 提供模型，**`peft`（Parameter-Efficient Fine-Tuning）** 实现 LoRA，**`trl`（Transformer Reinforcement Learning）** 提供现成的 `SFTTrainer`/`DPOTrainer`。
- **Unsloth**：优化过的 LoRA/QLoRA，快约 2 倍、省一半显存，适合中小规模。
- **DeepSpeed**（微软）：分布式训练优化，核心 **ZeRO（Zero Redundancy Optimizer）** 把占显存的东西分片到多卡。ZeRO-1 分片优化器状态，ZeRO-2 再分片梯度，ZeRO-3 连参数都分片，级别越高省显存越多、通信开销越大。
- **Megatron-LM**（NVIDIA）：超大模型首选，做 **张量并行（把单层矩阵切到多卡）** 和 **流水线并行（不同层放不同卡按流水线跑）**。
- **FSDP（Fully Sharded Data Parallel）**：PyTorch 原生参数分片，相当于 ZeRO-3 的官方替代。
- **Axolotl / LLaMA-Factory**：配置文件驱动，写个 YAML 就能跑。

**transformers + peft + trl 怎么用**（最小 LoRA SFT 骨架）：

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig
from trl import SFTTrainer, SFTConfig
from datasets import load_dataset

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-7B-Instruct")   # transformers 加载基座
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
ds = load_dataset("json", data_files="train.jsonl")["train"]              # datasets 加载数据

lora = LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05,                 # peft 定义 LoRA 配置
                  target_modules=["q_proj","k_proj","v_proj","o_proj"])

trainer = SFTTrainer(                                                     # trl 封装训练循环
    model=model, train_dataset=ds, peft_config=lora,
    args=SFTConfig(learning_rate=2e-4, num_train_epochs=3,
                   per_device_train_batch_size=4, gradient_accumulation_steps=4,
                   bf16=True, gradient_checkpointing=True, max_seq_length=4096))
trainer.train()
trainer.save_model("./my-lora-adapter")   # 存出的就是 LoRA adapter
```

你主要写"加载什么模型、喂什么数据、设什么超参"，训练循环 trl 封装好了。做 DPO 就把 `SFTTrainer` 换成 `DPOTrainer`、数据换成 chosen/rejected 对。

**Unsloth 怎么用**（这套的加速替代品，API 几乎一样，只换入口加载器）：

```python
from unsloth import FastLanguageModel
model, tok = FastLanguageModel.from_pretrained("unsloth/Qwen2.5-7B-Instruct",
                                               load_in_4bit=True)   # 一行开 QLoRA
model = FastLanguageModel.get_peft_model(model, r=16, lora_alpha=32,
                                         target_modules=["q_proj","k_proj","v_proj","o_proj"])
# 之后照样用 trl 的 SFTTrainer 训练
```

**什么时候用哪个**：要稳、生态全、团队协作 → `transformers+peft+trl`；单卡/资源紧、想训快、个人小实验 → Unsloth。两者不冲突，Unsloth 输出的也是标准 LoRA adapter，能无缝接回 trl 和 vLLM。

**Platform（提供算力/调度/实验管理的基础设施）**

- **AWS SageMaker / GCP Vertex AI / Azure ML**：云厂商托管训练平台。
- **Kubernetes + Kubeflow / Ray**：自建集群常用。
- **实验追踪**：**Weights & Biases（wandb）**、**MLflow**、TensorBoard——记录 loss 曲线、超参、指标。
- **数据/模型版本管理**：DVC、LakeFS。

> Amex 做企业 AI infra，内部多半是 SageMaker 或自建 K8s+Ray，配 MLflow 做 model registry。

### 一个典型最小可跑配置（LoRA SFT）

```yaml
model: Qwen2.5-7B-Instruct
method: lora
lora_r: 16
lora_alpha: 32
lora_dropout: 0.05
target_modules: [q_proj, k_proj, v_proj, o_proj]
learning_rate: 2e-4
num_train_epochs: 3
per_device_train_batch_size: 4
gradient_accumulation_steps: 4   # 有效 batch = 4*4 = 16

bf16: true
gradient_checkpointing: true
max_seq_length: 4096
```

## 5. 评估

- **自动指标**：任务相关，如分类的 accuracy/F1，生成的 **BLEU/ROUGE**（衡量生成文本与参考答案重合度），代码的 **pass@k**（生成 k 个解里至少一个通过测试的概率）。
- **Benchmark（基准测试集）**：**MMLU**（多领域知识考试）、**GSM8K**（数学应用题）、**HumanEval**（代码）等通用能力测试，检查有没有掉点（监控灾难性遗忘）。
- **LLM-as-a-Judge（用大模型当裁判）**：用强模型（GPT-4/Claude）给输出打分——正是 LLM evaluation platform 的范畴。
- **人工评估**：抽样人工标注，最可靠但最贵。
- **关键检查灾难性遗忘**：微调后跑一遍通用 benchmark，对比微调前。

## 6. 注册与部署

### 存储 + 注册：两个配合使用、都要做（不是二选一）

训练产物（权重 + config + tokenizer，或 LoRA adapter）：

1. **先存对象存储 S3 / GCS / Azure Blob**：存的是 **模型文件本体**（几十 GB 权重 或 几十 MB adapter）。它是个放大文件的仓库，便宜、能放海量数据，但只管"存字节"，不懂这些文件是什么、哪个是哪版。
2. **再登记到 Model Registry（模型注册中心）**：MLflow / SageMaker Model Registry / HuggingFace Hub（私有）。它 **不重复存大文件**，只记一条指向 S3 文件的记录，外加版本号、哪次训练产出、用了哪份数据（**血缘 lineage**）、当前是 staging 还是 production、评估指标、谁批准上线。

> 比喻：S3 是书架（实际放书），Registry 是图书目录卡（记录每本书叫什么、第几版、在哪个架子、能不能外借）。缺一不可。

### 部署 / Deploy

- **推理引擎**：**vLLM**（最主流，核心技术 **PagedAttention**——像操作系统管内存分页那样高效管注意力缓存，大幅提升吞吐）、**TGI（Text Generation Inference，HuggingFace）**、**TensorRT-LLM**（NVIDIA，极致性能）。
- **LoRA 多租户部署**：vLLM 支持 **multi-LoRA**——一个基座挂多个 adapter 动态切换，这是大公司爱用 LoRA 的关键。
- **服务化**：包成 API（FastAPI / **KServe**（K8s 上的模型服务框架）/ SageMaker Endpoint），K8s 自动扩缩容。
- **量化部署**：上线前常用 **GPTQ/AWQ/GGUF**（主流量化格式）把模型量化到 INT8/INT4 降显存、提速。

## 7. 监控与迭代

### 输出质量漂移（drift）

**漂移** 指模型上线后实际表现随时间慢慢变差，尽管模型本身一字没改。根因：模型在 **过去某时间点的数据分布** 上训练，而真实世界在变，新数据越来越不像训练数据。

- **数据漂移（data drift）**：输入分布变了。如训练时没有"某新监管政策""某新产品名"，上线几个月后这些高频出现，模型没见过、处理变差；用户提问方式、热点、黑话也会变迁。
- **概念漂移（concept drift）**：输入和正确答案的 **对应关系本身变了**。如"高风险"定义因监管变化而改变——同一条新闻去年判低风险、今年规则变了该判高风险，但模型还按老规则判。
- 还有工程性原因：上游数据格式变了、对接系统改了、用户群体变了。

**怎么应对**：持续监控关键指标（准确率、用户点踩率、置信度分布），明显下滑就触发"用新数据重新微调"——闭环回到数据飞轮。漂移检测正是数据飞轮要不要转下一圈的信号。

### 持续迭代

- **A/B 测试 / 灰度发布**：新模型先放小流量对比。
- **数据飞轮（data flywheel）**：线上 bad case 回收 → 进数据集 → 下一轮微调，形成持续改进循环。
